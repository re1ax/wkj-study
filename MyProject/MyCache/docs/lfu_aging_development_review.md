# Aging LFU 开发复盘

这次开发是在普通 LFU 的基础上增加频率老化。最终实现不仅要完成“频率减一”，还要保证多个索引结构、链表迭代器和统计数据始终一致。整个过程集中暴露了模板实例化、容器修改和派生状态维护方面的问题。

## 1. 为什么需要频率老化

普通 LFU 会长期保留历史热点。某个 key 早期被大量访问后，即使它后来不再活跃，仍可能凭借很高的历史频率占据缓存。

Aging LFU 在平均频率达到阈值后降低所有节点的频率：

```text
newFreq = max(1, oldFreq - 1)
```

频率最低保持为 1，节点不会因为一次老化直接从缓存中消失。持续老化会逐渐削弱旧热点的历史优势，让新的热点有机会留下来。

## 2. 一份数据存在多个视图

当前实现同时维护：

```text
m_nodeMap[key]      -> 节点和值
m_keyFreqMap[key]   -> key 的当前频率
m_freqMap[freq]     -> 该频率对应的 key 链表
m_iterMap[key]      -> key 在频率链表中的迭代器
m_minFreq           -> 当前最小频率
m_curTotalFreq      -> 所有节点频率之和
```

这些成员不是相互独立的数据，而是同一份缓存状态的不同视图。修改频率时，只更新其中一两个成员是不够的。

本次最重要的检查原则是：一次操作结束后，从任意一张表查到的频率和位置都必须相互对应。

## 3. 不要在遍历容器时修改容器结构

初版尝试遍历 `m_freqMap`，同时使用 `erase()` 或 `extract()` 修改它。这会让当前迭代器失效，后续循环可能出现未定义行为。

更合适的方式是事务式重建：

1. 创建新的频率表和迭代器表。
2. 从旧表读取每个节点。
3. 计算新频率并写入新表。
4. 重新计算最小频率和总频率。
5. 所有数据准备好以后再整体替换旧表。

这种方式需要一次 O(n) 遍历，但状态变化更清楚，也不会留下只更新一半的数据结构。

## 4. 映射前唯一，映射后不一定唯一

`unordered_map` 中每个旧频率只会出现一次，但经过老化后，不同旧频率可能映射到同一个新频率：

```text
old 1 -> new 1
old 2 -> new 1
old 3 -> new 2
```

因此不能为每个旧频率重新赋一个空链表，否则处理旧频率 2 时会清空旧频率 1 已经放入新频率 1 的节点。

正确的思维方式是“向目标频率桶追加”，而不是“为每个旧桶创建一个对应的新桶”。

## 5. Key、Value 和 Iterator 是三种不同概念

开发过程中曾尝试把一个链表迭代器赋给整张 `newIterMap`。这个错误反映出容器类型需要进一步拆开理解：

```text
newIterMap              -> 整张 unordered_map
newIterMap[key]         -> 某个 key 对应的迭代器
list.back()             -> 链表最后一个 key 的值
prev(list.end())        -> 指向链表最后一个节点的迭代器
```

`m_iterMap` 的作用是让 `increFreq()` 能在 O(1) 时间从旧频率链表中删除指定 key，所以保存的必须是迭代器，而不是 key 本身。

## 6. 统计值也属于核心状态

最初实现只在访问时增加 `m_curTotalFreq`，遗漏了两种情况：

- 新节点进入缓存时，它已经拥有初始频率 1，总频率应该增加 1。
- 节点被淘汰时，总频率应该减去被淘汰节点的频率。

如果总频率不准确，平均频率阈值就会在错误的时间触发，最终让老化策略偏离预期。

重建完成后直接根据所有新频率重新求和，比尝试通过复杂的增量公式修补旧值更容易验证。

## 7. 模板必须通过实例化检查

仅仅包含 `LfuCache.h` 不一定会编译 `IAgingLfuCache` 的全部成员函数。只有创建具体类型并调用相关接口后，编译器才会实例化对应代码：

```cpp
ICache::ILfuCache<int, std::string> cache(2, 3);
cache.put(1, "one");
```

这次多个类型错误都是通过最小实例化测试暴露的。以后新增模板类时，应该尽早创建一个最小测试目标，不要等全部实现完成后再编译。

## 8. 专项测试应该验证策略，而不只是接口

普通的 `put/get` 测试只能证明缓存可以使用，不能证明 Aging 策略生效。本次专项测试增加了：

- 频率 1 和频率 2 老化后合并，所有 key 仍然存在。
- 数千次重复老化后，链表迭代器仍然有效。
- 旧热点经过老化后，可以被新热点替代。
- 老化过程中的并发访问不会破坏缓存结构。
- 零容量缓存不会保存数据。
- 负容量缓存不会尝试淘汰空链表。
- 非正老化阈值会抛出 `std::invalid_argument`。

其中“新热点替代旧热点”是最能区分普通 LFU 和 Aging LFU 的行为测试。

## 9. 从复制实现到统一核心

初版为了先理解 Aging 算法，复制了普通 LFU 的成员和操作。这种做法适合算法探索，但稳定后会产生明显问题：

- `put`、`get` 和频率移动逻辑需要维护两份。
- 普通 LFU 的修复不一定会同步到 Aging LFU。
- 两套相同索引增加了状态不一致的风险。

重构时没有让 Aging 类直接访问普通 LFU 的私有状态，而是让 `ILfuCache` 本身支持两种构造模式：

```text
ILfuCache(capacity)                 -> 普通 LFU
ILfuCache(capacity, averageLimit)   -> 开启 Aging
```

统一核心维护唯一一份节点表、频率表和 `put/get` 实现。`IAgingLfuCache` 最终只剩一个构造包装：

```cpp
template <typename Key, typename Value>
class IAgingLfuCache : public ILfuCache<Key, Value> {
public:
    IAgingLfuCache(int capacity, int maxAverageFreq = 10)
        : ILfuCache<Key, Value>(capacity, maxAverageFreq) {}
};
```

这里的继承是安全的，因为派生类不访问基类私有成员、不重写核心算法，只负责选择开启 Aging 的构造方式。

## 10. 类型别名也有作用域

为了降低模板类型的阅读负担，两个类曾分别加入 `NodePtr`、`FreqMap` 和 `IterMap` 等别名。过程中出现了两个典型问题：

- `_Value` 的拼写错误导致后续大量模板错误。
- 定义在 `ILfuCache` 私有区域的别名，在另一个类中不可见。

这说明 `using` 只是类型的别名，不会突破 C++ 的作用域规则。模板编译出现大量报错时，应该优先修复最前面的类型错误，后面的报错往往只是连锁反应。

## 11. 参数边界必须明确

本次最终确定了两种不同的参数策略：

```text
capacity <= 0          -> 缓存保持为空，put 不生效
maxAverageFreq <= 0    -> 抛出 std::invalid_argument
```

容量为零可以自然表示关闭缓存，因此负容量也按空缓存处理。老化阈值为非正数则没有合理算法含义，直接抛出异常能尽早暴露调用错误。

抛出标准异常时需要创建异常对象：

```cpp
throw std::invalid_argument("maxAverageFreq must be greater than 0");
```

不能只写异常类型名。同时，使用 `std::invalid_argument` 的头文件应显式包含 `<stdexcept>`，不能依赖其他标准库头间接包含。

## 12. 当前实现仍可继续改进

后续可以按风险从低到高继续练习：

1. 明确定义不同旧频率桶合并后的同频淘汰顺序。
2. 比较“每次减一”和“减去阈值的一半”两种衰减策略。
3. 使用更精细的计时单位衡量重建开销。
4. 增加老化触发次数等内部指标，分析阈值与性能的关系。

## 13. 本次最重要的收获

这次真正困难的部分不是频率计算，而是维护数据结构不变量：

```text
算法正确 = 策略规则正确 + 所有索引保持一致 + 边界条件可验证
```

当一个类同时维护多张表时，可以优先采用“构造完整新状态，再一次性替换旧状态”的方式。它通常比原地修改更容易推理、测试和排查问题。

重构过程还补充了另一条经验：先用直接实现把算法做正确，再根据已经暴露的重复边界提取公共核心。抽象应该来自已经理解的共同点，而不是在算法尚未稳定时提前猜测。
